## 1. 빌드 실패를 설명하는 빌드

- **빌드 전 사전 검사** `bdg build --check` (빌드 창의 "검사" 버튼): 깨진 참조, 없는 파일, 플랫폼에서 지원하지 않는 텍스처 형식, 셰이더 컴파일 오류, 스크립트 컴파일 오류, 서명 키 누락을 **쿠킹 전에** 모두 찾아 목록으로 보여 줌.
- **단계마다 격리된 오류**: collect → cook → scripts → pack → output 중 **어느 단계, 어느 에셋에서, 왜** 실패했는지 한 줄로. 수천 줄 로그를 뒤질 필요 없음.
  ```
  ✗ [2/5] cook  Textures/T_Wall_N.png
     원인: 2049x2048 — ASTC는 블록 크기 배수가 필요
     고치기: 크기를 2048x2048로 (bdg fix T_Wall_N --resize)   또는 이 플랫폼에서 압축 형식 변경
  ```
- **실패해도 멈추지 않고 끝까지**: 오류를 모두 모아 한 번에 보여 줌(첫 오류에서 멈추지 않음).
- **증분·재현 가능**: 같은 입력이면 같은 결과(해시 캐시). "어제는 됐는데 오늘 안 됨"을 줄임.
- **CI가 커밋마다 빌드**: 실패를 출시 직전이 아니라 그 커밋에서 발견.
- **AI가 읽는 보고서**: `build-report.txt`의 오류 형식이 고정돼 있어 AI가 바로 고칠 수 있음.

## 2. 열다가 튕기지 않는 에셋 (에디터 안전장치)

- **텍스트 저장**: 그래프가 망가져도 텍스트 편집기로 열어 고치거나, `bdg validate Door.graph --fix`로 깨진 연결만 제거. 파일을 지울 필요가 없음.
- **열기 전에 검사**: 그래프·씬을 불러올 때 먼저 구조 검사(없는 노드 타입, 끊긴 연결, 순환 참조). 문제 노드는 빨간 "깨진 노드"로 표시하고 나머지는 정상으로 엶.
- **VM 보호**: Graph VM에 명령 수 예산(한 프레임 기본 1천만), 호출 깊이 제한, 메모리 제한. 넘으면 그 그래프만 멈추고 오류 위치(노드)를 강조. 에디터는 계속 동작.
- **Construction Script는 에디터에서 제한 시간**: 배치할 때 실행되는 스크립트가 오래 걸리면 중단하고 경고.
- **안전 모드 재시작**: 에셋을 여는 중에 크래시가 나면, 다음 실행 때 "마지막에 연 `Door.graph` 때문에 종료된 것 같아요" → 그 에셋을 **격리(열지 않음)** 한 채 에디터를 엶. 크래시 보고서도 같이 만듦.
- **자동 저장·복구**와 연결: 튕겨도 작업이 날아가지 않음.

## 5. 빠른 C++ 반복

| 언리얼이 느린 이유 | 비둘기 엔진 |
|---|---|
| 게임 코드가 거대한 엔진 헤더를 끌어옴 (`CoreMinimal.h` 등) | 게임 모듈은 **얇은 헤더**(`bdg/*.h`, C API 위의 C++ 래퍼)만 포함. 엔진 내부 헤더는 노출하지 않음 |
| 소스 빌드 엔진이면 엔진까지 다시 빌드 | 엔진은 **미리 빌드된 SDK**로 배포 (헤더 + 라이브러리). 사용자는 자기 모듈만 컴파일 |
| UHT(헤더 도구)가 매번 전체를 훑음 | 헤더 도구는 **바뀐 헤더만** 처리, 결과 캐시 |
| 큰 모듈 하나 | 기능별 **작은 모듈** 권장 (템플릿이 그렇게 생성), 미리 컴파일된 헤더(PCH)·유니티 빌드 자동 설정 |
| 라이브 코딩이 불안정 | 모듈 DLL **라이브 리로드**: 상태 직렬화 → DLL 교체 → 상태 복원. 실패하면 이전 DLL로 되돌림 |
| 게임 로직도 C++로 써야 하는 분위기 | 게임 로직은 **C#·Graph·Lua 권장**(핫 리로드 1초 안팎), C++는 성능·엔진 확장용 |
| 컴파일 캐시 없음 | sccache/ccache 자동 연결 옵션, 팀 공유 캐시 |

**목표 시간** (템플릿 게임, 일반 개발 PC — 측정으로 확정):

| 작업 | 목표 |
|---|---|
| 게임 모듈 `.cpp` 한 줄 수정 → 실행 중 반영 | **5초 이하** |
| 게임 모듈 헤더 수정 → 반영 | 15초 이하 |
| 템플릿 게임 전체 클린 빌드 | 60초 이하 |
| C# 수정 → 반영 | 2초 이하 |

## 6. 빨리 열리는 에디터

| 언리얼이 느린 이유 | 비둘기 엔진 |
|---|---|
| 모듈·플러그인 전부 로드 | 기능은 **패키지로 켜고 끔**, 쓰는 순간에 로드(지연 로드) |
| 처음 열 때 셰이더 수천 개 컴파일 | 셰이더 수를 줄이는 설계(순열 제한) + **해시 캐시** + 팀 공유 캐시. 컴파일 중에는 기본 셰이더로 먼저 표시 |
| 에셋 레지스트리 전체 스캔 | 에셋 DB **색인 캐시**(`.cache/assetdb`), 시작할 때는 파일 수정 시각만 비교해 바뀐 것만 다시 읽음 |
| 마지막 레벨을 전부 불러온 뒤에야 화면 | 에디터 화면 먼저 → 씬은 **점진 로드**(보이는 것부터), 진행 막대 |
| 어디서 느린지 알 수 없음 | 시작 과정 단계별 시간을 로그에 (`perf: startup ...`), `bdg profile --startup` |

| 템플릿 프로젝트 열기 → 조작 가능 | 3초 이하 | — |
