# 네트워크·공동 편집 대비 점검 (QUEUE 1-7)

작성 2026-11-23. 멀티플레이(N 트랙)와 공동 편집(C 트랙)은 1.0 이후에 만들지만, 바탕 구조가 지금 맞아야 나중에 뜯어고치지 않습니다. M1 끝에서 네 가지를 점검했습니다.

## 점검 결과

| 항목 | 결과 | 근거 |
|---|---|---|
| 영구 ID가 모든 오브젝트에 있음 | ✓ | 씬 오브젝트는 생성 때 `g<n>` ID를 받고, 실행 중 핸들(`Handle<SceneObject>`)과 분리됨. 삭제 후 Undo로 돌아와도 같은 ID. 테스트 `determinism: every object has a persistent id ...` |
| 모든 변경이 명령으로 직렬화됨 | ✓ | 에디터에서 씬을 고치는 길은 명령 버스뿐 (Inspector 필드, 복제, 삭제, 화면 낭독기의 값 설정도 `set` 명령). 씬을 직접 고치는 코드는 샘플 씬 불러오기(편집이 아님)뿐 — 코드 검색으로 확인. 명령은 JSON 한 줄(`{"cmd","target","args","source","t"}`) |
| 리플렉션이 바뀐 필드를 추적함 | ✓ (고침) | `Registry::Set`이 실제로 값이 바뀐 필드만 기록. 점검 중 발견: 에디터가 기록을 비우지 않아 세션 내내 쌓였음 → `EditorModel::Update`가 매 프레임 비움(나중에 복제 계층이 이 자리에서 가져감) |
| 명령 적용이 결정적 | ✓ | 무작위 편집 세션(설정·끌기 합치기·추가·삭제·이동·이름·컴포넌트·Undo/Redo·묶음, 여러 출처)을 ① 다른 버스에 한 줄씩 전달(공동 편집 흉내, 2010줄) ② JSONL 저장 후 같은 프로세스에서 재생 ③ **다른 프로세스**(`BidulgiTests --replay-dump`)에서 재생(1734줄) → 세 경우 모두 씬 덤프와 Undo 깊이가 같음. 에디터에서는 CI 7번이 Inspector 편집 로그를 다른 프로세스에서 재생해 비교 |

결정성을 지키는 장치:
- `add`는 받은 ID를 로그에 적고, 복제는 ID를 먼저 정해 넘김 → 재생해도 같은 ID.
- 연속 편집 합치기는 시계가 아니라 로그에 적힌 시각 `t`로 판단 → 재생해도 같은 Undo 단계.
- 실패한 명령·빈 Undo/Redo는 로그에 남지 않음.
- 값은 JSON 텍스트, float은 가장 짧은 왕복 표기 → 프로세스가 달라도 같은 글자.

## 나중 단계에서 풀어야 할 것 (지금은 기록만)

| 주제 | 내용 | 단계 |
|---|---|---|
| ID 충돌 | 두 에디터가 동시에 오브젝트를 만들면 둘 다 `g10`을 쓸 수 있음. 세션 서버가 ID 범위를 나눠 주거나 클라이언트 접두어(`g10@b`)를 붙임 | C-1 |
| 명령 순서 | 서로 다른 에디터의 명령은 세션 서버가 정한 한 순서로 모두에게 적용(현재 구조가 그대로 맞음). 충돌(같은 필드 동시 편집)은 나중 값 우선 또는 잠금 | C-1, C-2 |
| 작성자 | 명령에 `source`(ui·ai·script·terminal·replay)는 있음. 공동 편집에서는 사람별 `author` 필드 추가 | C-3 |
| Undo 범위 | 공동 편집에서 Ctrl+Z는 "내 명령만" 되돌려야 함 → 역명령을 그 시점 상태에 맞게 다시 계산 | C-2 |
| 복제 대상 | 게임 실행 중 복제는 `kReplicated` 필드만, 바뀐 필드 기록(`TakeChanges`)을 묶어 보냄 | N-2 |
